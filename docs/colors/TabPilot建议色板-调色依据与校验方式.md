# TabPilot 建议色板：调色依据与校验方式

> 定稿日期：2026-11-27　|　适用档位：`vivid-light` / `vivid-dark`（增强对比主题）
> 这份文档记录"建议色板为什么是这些值、用什么方法验证"，是 BUG-07 主题风格方案的核心设计依据。
> 可视化对照：[色块对照](tabpilot-group-colors.html)、[色度平面与 WCAG 面板](edge-colors-chromaticity.html)。

---

## 一、问题与目标

TabPilot 的页内标识（边框 / banner）颜色来自 `store.js` 里一张固定的历史 Chrome 浅色色板（现命名为“经典”），与浏览器原生分组色没有运行时关联。三个事实决定了"精确对齐原生"做不到：

1. `chrome.tabGroups` 只返回颜色**枚举名**，不暴露实际 RGB。
2. Chromium 的分组色是 `ui::ColorId` 语义 token，由浏览器内部 color pipeline 按明暗模式动态解析，扩展读不到。
3. Edge 在渲染层自建了一套映射——9 个枚举里 7 个统一压低饱和度、把明度收进窄带，`red` / `green` 两个槽位还换了色相（分别显示为"紫罗兰色""亮蓝色"）。

**目标**：做一套"主动增强对比"的色板，让 9 个颜色彼此尽量分得开，同时每个颜色还"像"原生那一个枚举，作为 Edge 默认主题。

---

## 二、使用的色彩空间与指标

调色和校验全部在 **CIELAB** 感知均匀空间进行，配合四个指标：

| 指标 | 含义 | 在本项目里的用途 |
| --- | --- | --- |
| **L\*** | 明度，0（黑）→ 100（白） | 拉开颜色的第三维度；Edge 把 9 色挤在 L\*43–50，是混淆的根因 |
| **a\*** / **b\*** | 红(+)↔绿(−) / 黄(+)↔蓝(−) | a\*–b\* 平面看色相与彩度分布 |
| **C\*** / **h** | 彩度 / 色相角 | 描述"多鲜艳""是什么色"，用于生成规则和主动偏离 |
| **ΔE00**（CIEDE2000） | 两色的感知色差 | **项目设计目标**：正常色觉下同一色板内 ≥ 20；与原生 ≤ 13 作为近似目标，不是普遍保证 |
| **WCAG 对比度** | 相对亮度比 `(L亮+0.05)/(L暗+0.05)` | 色块在白底 / 深底上是否看得清，≥ 3.0 达标（AA 图形元素） |

一个关键认知：**ΔE00 和 WCAG 量的是两件事**。ΔE00 含色相、彩度、明度，衡量"两个颜色像不像"；WCAG 只看亮度，衡量"边界看不看得清"。黄、橙是高亮暖色，色相极艳但亮度接近白底，WCAG 数字天然低——所以亮色要靠压暗而非描边来解决可读性。

## 三、调色依据

### 3.1 基准：Edge 原生色相骨架

以 **Edge 原生 9 色的色相**为骨架，不做"色相重排"式的激进方案（紫色分组配红框只会让用户更困惑）。色相归属按 Edge 定，不按 Chrome——因为 Edge 的 `red` 本就是紫罗兰、`green` 本就是亮蓝。

### 3.2 生成规则

1. **色相基准**：以 Edge 原生色相为基础，通常允许 ±5° 偏移；pink、cyan、深色 green 等主动偏离见 3.4。
2. **彩度下限**：不低于原生的 86%（深 `blue` 是唯一例外，只有 67%）。
3. **明度三档重排**：把 9 个色的明度拉开成三档（详见 3.3）。
4. **两条硬约束**：每格与原生 ΔE00 ≤ 13（"还是那个颜色"）；浅色在白底、深色在深底的对比度 ≥ 3（边框不被页面吃掉）。

未达标或主动偏离的几处见 3.4；真正"越界"（与原生 ΔE00 \> 13）的只有 `pink`。

### 3.3 为什么必须重排明度

Edge 把 9 个色的明度压进 **L\*43–50 这条窄带**，人眼只剩色相可用，而紫 / 紫罗兰 / 粉三色又只差 20°。拉开明度是**不动色相又能分开唯一办法**。

这也是色度平面图必须配一根明度标尺的原因：a\*–b\* 平面是固定 L\* 的二维截面，明度差被压掉了。例如浅色 `blue` 与 `green` 在平面上看着近（投影距离约 19），但 L\* 差 22.5，实际 ΔE00 有 22.8——区分几乎全靠明度撑着。

### 3.4 主动偏离与逐轮调校

| 色 | 调整 | 依据 |
| --- | --- | --- |
| `pink` | 色相 352°→18°，做成警示红 `#E3004E` | 整组唯一"一眼是红色"的槽位，标示需注意的规则；与原生差 15，是唯一越界格 |
| `cyan` | 色相 203°→180°、彩度 30→40（色域上限） | 从"灰蓝绿"变干净青绿，与 `blue`/`green` 簇的间距 29.7→37.4；与原生差 13.0，贴线 |
| `yellow` | L\*42→先提亮到 70→最终收到 58，`#B08500` | 提亮版白底对比度只有 2.30 需描边；收一档到 58 后升到 3.39、描边需求消除，且更像原生（ΔE00 回落到 8.7） |
| `orange`（浅） | 往黄挪 6°、彩度推到上限（h47→53、C75→78），明度压到 58，`#E66415` | 被 `pink`(18°) 与 `yellow`(84°) 夹住，红橙边界是人眼最钝段；只能靠色相 + 彩度拉开。白底 3.39 |
| `blue`（浅） | 转纯蓝：a\*22.7→13.3、L\*58.1→60.2，`#6984F4`→`#588FF5` | 原先与 `purple` 只差 20.3；往右下挪会撞 `purple`（降到 14.7），改往左回纯蓝后拉到 28.9，靠明度差维持与 `green` 的距离 |
| `green`（深） | 色相 256°→236°，`#508DB8`→`#3691B1` | 原是混淆对中心（purple↔green 17.3、green↔blue 19.9）；改明度是死路，改色相往青蓝移同时远离 purple 和 blue，混淆对清零 |
| `orange`（深） | 彩度 78→70、色相 58°→55°，`#FF8427`→`#FC863D` | C\*78 是全表异常值（第二名才 54.9），在一片灰白里过于扎眼；降到 70 并微拨色相后仍守住红橙 22.5 / 橙黄 23.2，且更接近原生 |

调校是**迭代**的：先观察问题（如"深橙太饱和""蓝和 green 平面看着近"）→ 数值实验找候选 → 验证会不会撞其他色 → 落地。每一轮都同时看 ΔE00、WCAG 和色度平面。

## 四、校验方式

### 4.1 ΔE00 两两区分度（主判据）

对每套色板的 9 色做全部 36 个两两组合（C(9,2)），用 CIEDE2000 算 ΔE00：

- **套系内最小 ΔE00 ≥ 20** 才算整套可分；低于 20 记为"混淆对"，必须清零或解释。
- **与原生 ΔE00 ≤ 13** 保证"还是那个颜色"，超出必须作为主动偏离说明理由。

结果（9 套色板横向对比）：

| 色板 | 最小 ΔE00 | 混淆对(\<20) |
| --- | --- | --- |
| Edge 浅 / 深 | 10.3 / 10.6 | 4 / 5 |
| Chrome 浅 / 深 | 14.6 / 13.9 | 2 / 5 |
| Firefox 浅 / 深 | 10.3 / 11.9 | 3 / 5 |
| TabPilot 现实现 | 19.2 | 1 |
| **建议浅（vivid-light）** | **22.8** | **0** |
| **建议深（vivid-dark）** | **21.2** | **0** |

建议色板把浅色最小从 10.3 提到 22.8、深色从约 10 提到 21.2，混淆对都清零。

### 4.2 色度平面 + 明度标尺（三维观察）

[色度分析页](edge-colors-chromaticity.html)用 a\*–b\* 平面展示色相 / 彩度分布，配 L\* 明度标尺补第三维，可切换 11 套数据、叠加全彩底图。专门用来发现"平面看着近、其实明度差很大"（如 blue/green）或"平面看着远、其实混淆"（色觉障碍场景）的情况。

### 4.3 WCAG 对比度（可读性）

对比面板做成每行一条连续长条、三段无缝拼接：左段白底分值、中段目标色块叠黑白字、右段深底分值。校验结论：

- **浅色套**：白底最低是 `blue` 3.15、`red` 3.21、`cyan` 3.27、黄橙各 3.39，**全部 ≥ 3**，无需描边。
- **深色套**：深底全部 ≥ 4.26，达标。
- 早期"提亮版"黄橙（2.30 / 2.95）低于 3 才需要 1px 内描边，收一档到 L\*58 后该结论作废。`custom` 档用户可能填到与页面同色的值，描边作为可选兜底由用户自行判断。

### 4.4 色觉障碍模拟（已知边界）

模拟 protan / deutan / tritan 三类常见色觉障碍后，深色 protan 的 `pink`/`grey` ΔE00 只有 2.4、deutan 的 `red`/`blue` 2.0、tritan 的 `pink`/`orange` 5.8；浅色 deutan 的 `red`/`blue` 7.4、`yellow`/`orange` 8.9。9 色相环本身救不了这些组合——**组名前缀是必需的第二维度**，"ΔE00 全部 \> 20"不等于所有用户都能分清。

### 4.5 算法校准

每次改色前，先用**未改动的色对**复现页面已有 ΔE00 值，确认 CIEDE2000 实现与页面一致，再重算全部色对并写回。避免算法 bug 导致数据错误。

## 六、已知边界

1. **不追求精确对齐原生**：页内标识只是大概的视觉提醒，深浅错配无所谓。这套表色相按 Edge 定，用在 Chrome 上时 `green` 与原生差 49.0、`red` 差 32.2、`pink` 差 22.0；切换主题后标识与分组标签整体错位是已知代价，设置页需写明"只影响页内标识，不改变分组颜色"。
2. **色觉障碍需靠文字兜底**：见 4.4，颜色本身无法覆盖所有色觉类型。
3. **验证是"当前满意"而非"数学最优"**：调色在连续空间里找平衡，没有唯一正确答案；定稿表示当前数据达标且观感可接受。

## 七、插件主题映射

实现中的色值统一维护在 `src/core/color-themes.js`。Firefox、Chrome、Edge 原生浅 / 深主题分别取分析页 FFL / FFD、CHL / CHD、EWL / EWD；Edge 原生使用 Windows 基准，macOS 采样保留作对照。增强对比取 RL / RD，“经典”取 TPL。主题只影响页内标识和设置页色块 / 预览，不改变原生群组的颜色枚举。

Firefox、Chrome、Edge 构建默认分别为 `firefox-light`、`chrome-light`、`vivid-light`。配置中的 `colorTheme` 可选，缺省时采用当前构建默认；显式选择随保存和配置导入导出保留。所有主题固定明暗，不自动跟随系统。
